# DSM Log: 2026-04-25 - Project Audit & "Council of Agents" Kickoff

**Goal:** Conduct a comprehensive audit of the SpendSense project to identify critical shortcomings across all specialized domains.

---

## 📋 PM Agent (Product Manager)
**Status:** 🚩 AT RISK
**Shortcomings:**
- **Incomplete Domain Coverage:** We are currently an "Expense" tracker, not an "Income" or "Refund" tracker. This makes our ledger incomplete for a true financial overview.
- **Weak Deduplication:** Our deduplication logic is currently body-hash based and exists only on the client. We lack cloud-side idempotency.
- **Limited Bank Support:** The local parser only supports 4 banks. We need a more scalable strategy for the 100+ UPI-enabled banks in India.

## 💻 Flutter Agent (Lead Developer)
**Status:** 🏗️ TECHNICAL DEBT ALERT
**Shortcomings:**
- **God Object Pattern:** `AppState.dart` is bloated (orchestration + parsing + sync + UI state). It needs to be refactored into domain-specific services.
- **Blocking Sync:** Confirmation and sync are sequential. Confirming 10 transactions in a daily digest blocks the UI for 5-10 seconds.
- **State Inconsistency:** We are mixing `SharedPreferences` and `SecureStorage` for configuration, leading to migration risks.

## 🧪 QA / SDET Agent (Test Automation)
**Status:** 📉 LOW COVERAGE
**Shortcomings:**
- **Zero E2E/UI Tests:** We have unit tests for models, but no automated validation that an SMS actually results in a transaction appearing on the Home Screen.
- **Brittle Parsing:** Our regex-based parsing is a "black box" that isn't being tested against a wide corpus of actual bank SMS variations.
- **Regression Risk:** No automated regression suite to ensure new logic doesn't break established SMS triggers.

## 🎨 UX/UI Agent (Designer)
**Status:** 💅 LACKS POLISH
**Shortcomings:**
- **Notification Overwrites:** We use a single ID for all transaction popups. If two transactions happen back-to-back, the second one "eats" the first.
- **Invisible Sync:** There is no "Syncing..." spinner or health status. Users don't know if their data is actually in Google Sheets until they check the sheet.
- **Confirmation Fatigue:** The daily digest UI is purely functional and lacks the "vibe" of a modern financial app.

## 🔒 SecOps Agent (Cybersecurity)
**Status:** 🛠️ IN PROGRESS (SPEND-005)
**Shortcomings:**
- **Plaintext Ledger:** The SQLite database is not encrypted. Any app with root or backup access could read the user's entire financial history. (Current Focus)
- **Unauthenticated Backend:** The Google Apps Script webhook is open to "Anyone." There is no shared secret or API key check to prevent malicious data injection.
- **Foreground Leak:** Background SMS processing logs may contain PII in the console (unmasked amounts/sender IDs).

**Update [17:02]:** Starting implementation of `sqflite_sqlcipher`. Collaborating with FlutterDev to migrate `LocalStorageService`.

## ⚙️ DevOps Agent (Infrastructure)
**Status:** 🧱 MANUAL PROCESSES
**Shortcomings:**
- **No CI/CD:** We are building APKs and running tests manually. No GitHub Actions to catch PR regressions.
- **Non-Idempotent Sync:** If a sync fails midway, retrying results in duplicate rows in Google Sheets.
- **No Crash Reporting:** We have no Sentry or Firebase Crashlytics. We are blind to production crashes.

## 💬 Council Discussion: SPEND-010 (Real SMS Ingestion Failure)
*(Following the new 4-Iteration Planning Rule)*

### Iteration 1: Understanding the Issue
**Orchestrator:** The `SmsService` currently uses `Telephony.instance.listenIncomingSms` with `listenInBackground: true`. It works for simulated notifications, but real SMS messages are not triggering this on physical Android devices.
**Lead FlutterDev:** We have `RECEIVE_SMS` and `READ_SMS` permissions in the `AndroidManifest.xml`. The dart background handler `_backgroundSmsHandler` is correctly set up.
**Orchestrator:** The issue is that the OS is not delivering the broadcast intent to the app when it's closed or in the background because the plugin relies on implicit broadcasts.

### Iteration 2: Refinement & Opinions
**🤖 Android Specialist:** That's exactly it. On Android 11+, implicit broadcasts like `android.provider.Telephony.SMS_RECEIVED` are only delivered to apps in the background if they have a static `BroadcastReceiver` explicitly defined in their manifest. The `telephony` plugin doesn't dynamically inject this for us.
We must add a `<receiver>` block in `android/app/src/main/AndroidManifest.xml` targeting `com.shounakmulay.telephony.sms.IncomingSmsReceiver` with the `SMS_RECEIVED` intent filter. Without it, the app is deaf to real SMS when backgrounded.

### Iteration 3: Edge Cases & Probable Bugs
**🧪 QA:** What about reboots? Will the app wake up and process SMS if the phone restarts and the user hasn't opened SpendSense yet?
**🤖 Android Specialist:** Yes, static manifest receivers are triggered by Android even after a reboot. The OS delivers the `SMS_RECEIVED` broadcast, waking up the app's receiver.
**🧪 QA:** And what about App Standby Buckets or Doze mode? The background isolate might get killed before it finishes parsing and saving to `LocalStorageService`.
**🤖 Android Specialist:** Good point. To ensure our `_backgroundSmsHandler` isolate gets enough execution time to finish the DB write, we should also request the `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` permission.
**💻 Lead FlutterDev:** We also need to verify that `SmsService.instance._isPaymentSms` is safe to call from the background isolate without initializing the full app state. It's a pure static function, so it's completely safe.

### Iteration 4: Final E2E Implementation & Testing Plan
**Orchestrator:** The plan is crystallized.

**Implementation:**
1. **Modify `AndroidManifest.xml`**:
   - Add `<uses-permission android:name="android.permission.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS" />`.
   - Add the explicit `<receiver>` block for `IncomingSmsReceiver` inside the `<application>` tag, listening for `android.provider.Telephony.SMS_RECEIVED`.

**Testing Plan:**
1. **Physical Device Setup:** Install the updated APK on a physical Android device.
2. **Background Test:** Swipe away/kill the app entirely. Send a test transaction SMS to the device. Open the app and verify the transaction was captured and appears in the ledger.
3. **Reboot Test:** Restart the device. Do not open the app. Send a test SMS. Open the app and verify it was captured.
