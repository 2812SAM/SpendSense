## 2. Application Understanding

**What it is:** SpendSense is a local-first, Android-first, zero-setup expense tracker for Indian UPI/bank-SMS users, built in Flutter/Dart.

**Core loop:**
1. `SmsService` (wrapping a vendored `telephony` plugin) detects incoming payment-like SMS, foreground or background.
2. `AppState` (`lib/state/app_state.dart`) — the single orchestrator — runs a classification pipeline in order: SHA-256 fingerprint dedup check → `LocalParserService` (regex, 4 Indian banks) → `merchant_memory` SQLite lookup → optional `ClaudeService` (Anthropic API) → manual-review fallback.
3. Every transaction, regardless of path, is written to a local SQLite ledger (`LocalStorageService`, encrypted via `sqflite_sqlcipher`) **before** any network sync is attempted.
4. Low-confidence transactions surface via a notification popup (`PopupScreen`) or a nightly 9 PM digest (`DigestScreen`); both write back through `AppState.confirmCategory`/`confirmWithVoice`.
5. Confirmed transactions optionally sync to a Google Apps Script webhook (`SheetsService` → `backend/apps_script.js`), with local retry on failure.

**Architecture style:** ad-hoc layered architecture (not Clean Architecture, not BLoC) — `core/` (constants), `models/` (plain Dart data classes with manual `toMap`/`fromMap`), `services/` (singletons via static `.instance`, but constructor-injectable for tests), `state/` (one `ChangeNotifier`, `AppState`, as the sole orchestrator/state machine), `ui/screens/` (5 screens, `Provider`/`Consumer` for state access). This is a reasonable "ad-hoc / lightweight service-locator" architecture for an app this size.

**State management:** `provider` package, single `ChangeNotifier` (`AppState`) exposed via `ChangeNotifierProvider` in `main.dart`.

**Dependency injection:** Manual constructor injection with `?? Service.instance` defaults — not a DI framework (no `get_it`, no `injectable`). Confirmed in `AppState`'s constructor and mirrored in `SheetsService`/`SecureStorageService` for testability.

**Routing:** Flutter's built-in `Navigator` with named routes (`routes: {}` map) plus `onGenerateRoute` for routes needing arguments (`/popup`, `/setup-settings`). No `go_router`/`auto_route`.

**Networking:** raw `http` package, two clients: `ClaudeService` (Anthropic Messages API) and `SheetsService` (POST to an Apps Script webhook URL).

**Auth:** none in the traditional sense — "auth" here is a user-supplied Claude API key and a webhook URL, both optional, stored via `SecureStorageService` (`flutter_secure_storage`).

**Local storage:** SQLite via `sqflite_sqlcipher` (encrypted), schema version 4, three tables: `transactions`, `merchant_memory`, `custom_categories`. Plus `shared_preferences` for a few flags (`onboarding_done`) and a background SMS queue. Plus `flutter_secure_storage` for secrets (API key, webhook URL, DB encryption key).

**Models/entities:** `MyTransaction` (`lib/models/transaction.dart`), `MerchantMemory` (`lib/models/merchant_memory.dart`). Both hand-written, no code generation.

**Services:** `SmsService`, `ClaudeService`, `LocalParserService`, `LocalStorageService`, `NotificationService`, `RecentTransactionsService`, `SecureStorageService`, `SheetsService`, `VoiceService`, `DigestScheduler` (thin wrapper over `NotificationService`).

**Screens/widgets:** `HomeScreen`, `SetupScreen` (onboarding + settings, dual-mode), `PopupScreen`, `DigestScreen`, `DeveloperToolsScreen` (debug-only, gated by `kDebugMode`). No shared/reusable widget library folder — small private widgets live at the bottom of each screen file, which is appropriate at this scale.

**Utilities/constants:** `lib/core/constants.dart` (single `AppConstants` static-const class) and `lib/core/debug_samples.dart` (sample SMS strings for the debug screen).

**Themes:** one `ThemeData` inline in `main.dart`, Material 3, no separate theme file.

**Localization:** none (no `.arb` files, no `flutter_localizations`). English-only, India-specific formatting done by hand (`_formatDate`, `_formatTime` in `transaction.dart`).

**Assets:** **none.** `pubspec.yaml` has no `assets:` section, and no `assets/` directory exists anywhere in the project. All "images" seen (app icons, web icons) are standard Flutter-generated platform assets under `android/`, `ios/`, `web/`, `macos/`, `windows/`, `linux/`.

**Code generation:** declared (`build_runner`, `json_serializable` dev dependencies) but **not used** — no `@JsonSerializable`, no `part '*.g.dart'`, no generated `.g.dart` files anywhere in `lib/`. The only generated/mock file in the whole repo is `flutter_application_1/plugins/telephony/test/telephony_test.mocks.dart`, which belongs to the vendored third-party plugin, not the app.

**Tests:** 12 files under `test/` (unit + one widget test) + 1 file under `integration_test/` (13 test files total). Coverage exists for: transaction model, constants, local parser, local storage (incl. migration), secure storage, sheets service, claude service, recent transactions, app state, deduplication, and one widget test (popup screen). No dedicated tests for `SmsService`, `NotificationService`, `VoiceService`, or `DigestScheduler` in isolation (they're exercised indirectly through `AppState` tests).

**Platform-specific code:** Android is the only functionally complete platform (SMS ingestion requires it). `ios/`, `macos/`, `linux/`, `windows/`, `web/` are present and buildable but are default Flutter scaffolding — no custom native code beyond the default `MainActivity`/`AppDelegate`/`MainFlutterWindow` templates. iOS's `RunnerTests.swift` and macOS's `RunnerTests.swift` are the untouched default empty XCTest stub.

**Build configuration:** standard Flutter Gradle (`android/app/build.gradle.kts`), namespace/applicationId `com.spendsense.app`, **release builds still use debug signing** (documented as a known gap in `SpendSense_Repository_Context.md` and `SpendSense_Alpha_Launch_Checklist.md`).

**CI/CD:** one GitHub Actions workflow, `.github/workflows/copilot-setup-steps.yml` — runs `flutter pub get`, `flutter analyze`, `flutter test --coverage`, `dart format --set-exit-if-changed`, all scoped to `flutter_application_1/`. This workflow is scoped only to itself (triggers on changes to the workflow file), so it is **not** actually a general PR/push CI gate for the app today — see Section 22.

**Developer tooling:** a debug-only in-app screen (`DeveloperToolsScreen`) for SMS simulation and DB wipe; no CLI scripts, no `Makefile`, no `scripts/` directory.

**Environment configuration:** `.env.example` documents `CLAUDE_API_KEY`, `SHEETS_WEBHOOK_URL`, OAuth and keystore variables — but **no `.env` loading mechanism exists in the Dart code** (no `dotenv` package in `pubspec.yaml`, no `flutter_dotenv` import anywhere). The actual runtime configuration mechanism is the in-app `SetupScreen`, which writes directly into `SharedPreferences`/`SecureStorageService`. `.env.example` and `SECURITY.md`'s "Step 2" code sample describing `dotenv` usage describe a mechanism that was never implemented — see Section 9/22.

## 4. Current Problems

### A. Documentation sprawl and duplication
- Three files describe "how an AI agent should work on this repo" with overlapping and slightly contradictory content: `GEMINI.md`, `.github/copilot-instructions.md`, `Get_Started.md`.
- `SpendSense_Repository_Context.md` (the best single architecture doc) is **partially stale**: claims DB schema version 2 (actual: 4), claims no deduplication exists (actual: SHA-256 fingerprinting is implemented and tested), claims minimal test coverage (actual: 13 test files exist covering most services).
- `SpendSense_Codebase_TODO.md` has a corrupted tail — lines 60-79 contain garbled, repeated fragments of the "Build Order" list (evidence of a bad find/replace by a prior AI edit), e.g. `"Manifest Fixes** (Foundation)."` repeated four times with decreasing indentation-like fragments.
- `feature_discussion/` is a 23-file dated audit trail (5 date folders, plus a `dsm_logs/` subfolder, plus one loose `kanban_board.md`) of AI-generated implementation plans and execution reports, mandated by `GEMINI.md`/`copilot-instructions.md`/`Get_Started.md`. This is valuable history but is mixed into the live project root, one level above `lib/`.

### B. Duplicated AI-skill packaging (three copies of the same two skills)
- `skills/spendsense-sync/SKILL.md` and `.gemini/skills/spendsense-sync/SKILL.md` are byte-identical (verified with `diff -rq`).
- `skills/zero-hurdle-onboarding/` and `.gemini/skills/zero-hurdle-onboarding/` (including the `references/` subfolder) are byte-identical.
- `spendsense-sync.skill` and `zero-hurdle-onboarding.skill` at the repo root are ZIP archives (verified via file header `PK\x03\x04`) containing the exact same `SKILL.md`/`references/*.md` content again — a third copy, and a binary one, committed to git.
- The `zero-hurdle-onboarding` skill's own instructions reference a file, `flutter_application_1/feature_discussion/Zero_Hurdle_Implementation_Plan.md`, that does not exist at that path (the actual plan is `feature_discussion/2026-04-19/Setup_Screen_Removal_Plan.md`). The skill is already internally stale.

### C. One confirmed-obsolete file
- `flutter_application_1/android_manifest_additions.xml` lists permissions and a commented-out `SmsReceiver`/`BootReceiver` design that were never implemented natively (SMS handling is done entirely through the `telephony` Flutter plugin, confirmed — `MainActivity.kt`/`AppDelegate` have no custom receivers). Every permission it lists (`RECEIVE_SMS`, `READ_SMS`, `INTERNET`, `RECORD_AUDIO`, `FOREGROUND_SERVICE`, `RECEIVE_BOOT_COMPLETED`, `POST_NOTIFICATIONS`) is already present in the live `android/app/src/main/AndroidManifest.xml`. `SpendSense_Repository_Context.md` itself already flags this file as "legacy/should be cleaned up."

### D. Unused declared dependencies
- `permission_handler`: zero imports anywhere in `lib/` or `test/`. Permission requests are actually done through `telephony`'s own `requestSmsPermissions`, the Android notification plugin's `requestNotificationsPermission`, and `speech_to_text`'s own permission prompt.
- `intl`: zero imports anywhere in `lib/` or `test/`. Date/time formatting is hand-rolled in `transaction.dart` and the UI screens.
- `json_annotation` + the `build_runner`/`json_serializable` dev-dependency pair: zero `@JsonSerializable` annotations, zero `part '*.g.dart'` directives, zero generated `.g.dart` files anywhere in `lib/`.

### E. Branding/identity inconsistency (cosmetic, repo-wide)
- Dart package name: `spendsense` (`pubspec.yaml`).
- Android application ID/label: `com.spendsense.app` / "SpendSense" (correctly rebranded).
- Folder name, iOS `CFBundleName`/`CFBundleDisplayName`, web `manifest.json` `name`/`short_name`, web `index.html` `<title>`: all still `flutter_application_1` / "Flutter Application 1" — the default `flutter create` scaffold identity, never renamed.

### F. Documentation describes an unimplemented mechanism
- `.env.example` and `SECURITY.md` both describe loading secrets via a `dotenv`/`flutter_dotenv` package. Neither package is in `pubspec.yaml`, and no code in `lib/` reads a `.env` file. The real (and correctly implemented) mechanism is the in-app `SetupScreen` writing to `SecureStorageService`. This makes `.env.example`/`SECURITY.md` partially misleading to a new contributor.

### G. Dead/unwired configuration constant
- `AppConstants.prefDigestTime` (`lib/core/constants.dart:18`) is declared and documented as "reserved for future configurable digest time" but is never read anywhere in `lib/` or `test/`. Not a file-level issue, but worth tracking.

### H. Git hygiene
- No secrets, build artifacts, or IDE files are actually tracked in git (verified: `git ls-files` count matches `find` count exactly, and `git status` is clean). `.gitignore` is comprehensive and mostly correct. The only hygiene issue is the **binary `.skill` zip archives being committed** (see B above) — binary build-artifact-like files generally should not be tracked directly.

### I. Split repository root (see Section 0)
- The git root and the Flutter project root are not the same directory. Not a defect per se, but it is unusual and increases onboarding friction (many IDEs/tools assume `pubspec.yaml` is at the repo root).

## 11. AI Documentation Rules

**Where temporary AI work goes, and whether it is committed:**
- Adopt a `.ai/` (or reuse the existing `.gemini/` naming convention, but only for *scratch* material, not for skill definitions — see below) directory for in-progress AI planning material: draft plans, scratch notes, exploratory analysis.
- Add `.ai/` to `.gitignore`. Temporary AI planning material should **not** be committed by default.
- If a plan or execution report has genuine lasting value (it explains *why* a non-obvious decision was made), it should be promoted deliberately into `docs/decisions/` or `docs/architecture/` as a normal, reviewed documentation change — not auto-committed as a dated file next to the source tree. This directly replaces the current `feature_discussion/YYYY-MM-DD/*_Plan.md` + `*_Execution.md` mandate in `GEMINI.md`/`copilot-instructions.md`/`Get_Started.md`, which is what produced the 23-file sprawl this plan is now archiving.
- **Long-term engineering documentation** goes under `docs/development/` (guides, standards, TODO backlog).
- **Architecture decisions** go under `docs/architecture/` (system-level "how it works and why") and `docs/decisions/` (point-in-time strategic choices, roadmaps, checklists).
- **Feature documentation** goes under `docs/features/<feature-name>.md`, one file per feature, created only when a feature is non-trivial enough to need it — not one file per work session.
- **Troubleshooting** write-ups go under `docs/troubleshooting/<topic>.md`.
- **Plans**: day-to-day implementation plans should generally **not** be committed at all. If the team wants an audit trail, use git commit messages and PR descriptions (which are already durable and searchable) rather than parallel Markdown files. Reserve committed plan documents for genuinely large, cross-cutting initiatives, and put those under `docs/decisions/`, not scattered at the project root.
- **AI skill definitions** (`skills/*/SKILL.md`) are a different category from AI *working* material — they are reusable automation, not disposable notes. Keep exactly one canonical copy (`skills/`) in git. Do not also maintain a tool-specific mirror (`.gemini/skills/`) or packaged zip exports (`*.skill`) in version control; if a specific AI tool requires its own directory convention, generate that copy at tool-invocation time (or via a documented, gitignored build step) rather than committing a second source of truth.

**Existing AI instruction files — investigated:**
- `GEMINI.md` and `.github/copilot-instructions.md`: **complementary in intent, but largely duplicated in content.** Both describe the same architecture, the same mandates, the same file responsibility table, and the same dated-plan-file workflow. Recommendation: `copilot-instructions.md` becomes the single source of truth (it is the more complete of the two); `GEMINI.md` is merged and deleted (Section 8).
- `Get_Started.md`: **fully duplicated** by the "Development Workflow" section of `copilot-instructions.md`. Merge and delete (Section 8).
- No `CLAUDE.md` or `AGENTS.md` file exists anywhere in the repository (checked with a recursive case-insensitive filename search). If one is introduced later, it should either point at `.github/copilot-instructions.md` as the canonical source, or that content should be renamed/moved to whatever becomes the new single-source file — do not let a fourth copy start.

## 20. Repository Governance Rules

**Source code:**
- Screens live in `lib/ui/screens/`; there is no separate reusable-widget folder today because there is no cross-screen widget duplication — introduce `lib/shared/widgets/` only when a second screen needs to reuse a widget already defined elsewhere (extract at the point of second use, not preemptively).
- Models live in `lib/models/`, are immutable, and use `copyWith` — keep following this convention; do not introduce direct field mutation.
- Services live in `lib/services/`, one per external integration or storage concern, exposed via a static `.instance` singleton but constructor-injectable for tests (`ServiceX({Dep? dep}) : _dep = dep ?? Dep.instance`) — keep following this pattern for new services rather than introducing a DI framework, which would be a disproportionate change for this app's size.
- All transaction-lifecycle business logic stays centralized in `lib/state/app_state.dart` — do not scatter classification/persistence logic into UI widgets or into new services directly.
- Constants live in `lib/core/constants.dart`; if this file grows past a few hundred lines, split by concern (e.g. `notification_constants.dart`, `db_constants.dart`) rather than continuing to grow one file — not needed today at ~90 lines.
- Configuration values (API endpoints, model names) stay in `AppConstants`, never hardcoded inline in a service.

**Documentation:**
- Long-term docs live under `/docs` (Section 10's structure). No new Markdown file should be created at the repository root or at the Flutter project root without a clear reason it belongs in the small root allowlist (README.md, SECURITY.md — see Section 11).
- Before creating a new doc, check whether an existing one under `/docs` already covers the topic and should be extended instead.

**AI-generated artifacts:**
- Follow Section 11 exactly: scratch/working material in a gitignored `.ai/` directory; anything worth keeping gets promoted deliberately into `/docs` through a normal reviewed change, not auto-committed as a dated file.
- Never let a skill/instruction file exist in more than one location. `skills/` is canonical; do not create tool-specific mirrors.

**Assets:**
- If custom assets are introduced in the future (there are none today), group them under a top-level `assets/` directory inside `flutter_application_1/`, subdivided by type (`assets/images/`, `assets/icons/`, `assets/fonts/`), and declare them explicitly in `pubspec.yaml`'s `flutter: assets:` section rather than relying on implicit platform-default assets.

**New features:**
- For a feature small enough to fit the current pattern (a new screen + a new service), follow the existing layer-first convention (`lib/services/`, `lib/ui/screens/`, orchestration in `AppState`).
- For a feature large and self-contained enough to warrant its own module (per `Product_Vision_and_Roadmap.md`'s bigger items, e.g. "Trip/Tour Mode"), introduce `lib/features/<feature_name>/` with its own internal structure, and document the decision in `docs/decisions/`. Do not retrofit existing screens into a `features/` structure just for consistency — only new, genuinely separable feature code should move that way.

**Temporary files:**
- Experimentation and scratch work belongs in the gitignored `.ai/` directory or in a local, uncommitted branch — never as a committed root-level file with a name like `TEST.md`, `scratch.dart`, or similar.

**Generated code:**
- None is currently in active use in the app itself (only the vendored plugin's test mocks). If `json_serializable`/`build_runner`/Riverpod-generator/etc. are introduced later, generated `*.g.dart` files should be committed alongside their source (standard Flutter convention) and regenerated via `flutter pub run build_runner build` as part of the normal dev workflow — do not hand-edit generated files.
